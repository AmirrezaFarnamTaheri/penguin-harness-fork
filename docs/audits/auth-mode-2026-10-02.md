# I4 — Effective authentication mode: one pure resolver (2026-10-02)

I4 asked for a single decision point: whether a request must authenticate is derived from the
configured policy and the **trusted** bind address, never from anything a caller can set. This
receipt records the matrix (I4.1), the resolver and its default (I4.2), the middleware/app wiring
through that resolver (I4.3), and the revert-and-see evidence.

## Baseline

- Parent commit `06d733b6` (I1). Linux x64, Node v22.22.3, pnpm 11.18.0, vitest 4.1.11.
- Before this slice **no `authMode` code existed anywhere**: the gate was unconditional
  (`authMiddleware` always required a Bearer or a session), health was public only because
  `healthRoutes` is mounted above the gate, and the HMR gate re-derived its own loopback test from
  `deps.config.host`. The archive card records the pre-existing decision: "keep the old config
  parser but call the new pure resolver".

## I4.1 — The matrix

| `PENGUIN_AUTH_MODE` | Bind class (examples) | Effective | Endpoint requirements |
| ------------------- | --------------------- | --------- | --------------------- |
| `auto` (explicit) | loopback — `127.0.0.1`, `::1`, `localhost` | `off` | no credential required; identity resolved when presented, else the local-operator grant |
| `auto` (explicit) | unspecified — `0.0.0.0`, `::`, `*` | `all-except-health` | credential required for everything except the six probe paths |
| `auto` (explicit) | LAN — `192.168.1.10`, `server.lan`, `eth0` | `all-except-health` | as above |
| `off` | any | `off` | as loopback above |
| `all-except-health` | any | `all-except-health` | as above |
| anything else | any | **rejected** at config resolution | process does not start with a guessed mode |

Public endpoints under `all-except-health` are enumerated exactly as `healthRoutes` serves them:
`/health`, `/health/ready`, `/health/metrics`, `/api/health`, `/api/health/ready`,
`/api/health/metrics`. Not a prefix: `/api/health/unknown` and `/api/health/../me` are **not**
public (the path is normalized before matching, so the exemption is a property of the endpoint,
never of a spelling). Runtime-owned prefixes (`/api/auth`, `/api/desktop`, `/api/hmr`,
`/api/install`, `/api/instance`) are mounted in other layers, never reach this gate, and are
therefore deliberately not listed here.

## I4.2 — Decision: the shipped default stays `all-except-health`

The card specifies `Auto→Off` on loopback. That mapping is implemented exactly, but the
**default configured policy is `all-except-health`**, not `auto`, and this is a recorded decision
rather than a silent choice:

- Flipping the default would silently drop authentication on every existing loopback install
  (today the shipped behavior on `127.0.0.1` is "session required"), and `/api/me` would start
  answering 200 for anonymous callers — which is what the web app uses to decide whether to show
  the sign-in screen.
- Evidence for the blast radius: 52 `401` assertions across 20 server suites plus the browser
  login/first-login flows assume the gated default; `off`-by-default would invalidate them and
  remove the first-login/setup path from the loopback product experience.
- `auto` is implemented, tested, and one environment variable away for a loopback deployment that
  explicitly wants the local-convenience mode. **Reopen condition:** the product decision to make
  loopback deployments credential-free by default — the flip is one constant in
  `parseConfiguredAuthMode`'s fallback, and must land with the 401-assertion and login-flow
  updates as its own reviewed package.

## I4.3 — Wiring

- `resolveServerConfig` parses `PENGUIN_AUTH_MODE` (blank/missing → the default; a typo **throws**)
  and calls `resolveAuthMode(configured, host)` once, publishing the effective mode as
  `config.authMode` (plus `authModeConfigured`). Every consumer reads that decision.
- `authMiddleware(auth, trustProxy, policy)` applies the policy: a public path under
  `all-except-health` skips the gate; otherwise identity resolves Bearer → session cookie → (under
  `off`) the boot's own local-operator grant via `AuthService.localApiToken()` +
  `authenticateApiToken`. Under `all-except-health` with no credential it is the same 401 as
  before. Under `off` with no grant available it is **also** 401: missing configuration fails
  closed instead of inventing an identity.
- `createRuntimeApp`/`createApp` build one policy from config and hand the same object to every
  gate they mount (desktop-update, machine proxy, `/api/*`); `hmr/routes.ts` derives the same
  policy for its own cookie gate. Request headers are never an input.

### Unobservable mutation (recorded, not asserted)

`if (policy.decision.requiresAuth && policy.isPublicPath(...))` → `if (policy.isPublicPath(...))`
survived the suite. It is **equivalent under the current policy**, because `authPolicyFor` returns
`publicPaths = []` (and `isPublicPath === false`) whenever `requiresAuth` is false. The guard is
kept deliberately: it makes "every request reaching a handler has an identity in `c.var`" an
invariant of the middleware rather than of one policy implementation — the bug this fixed during
development was exactly an `off` policy skipping identity resolution and 500ing handlers on an
absent user.

## Compatibility

- **Default behavior is unchanged** (`all-except-health`): the same routes are public, the same
  routes 401, and the existing 215-case auth/health/desktop/hmr/first-login set passes untouched.
- **Opt-in change**: `PENGUIN_AUTH_MODE=auto` on a loopback bind (or `=off` anywhere) makes
  anonymous requests the built-in admin, reported as `sessionVia: "token"` (the local-operator
  grant is the same authority the API token encodes). Operators who need the old behavior set
  `PENGUIN_AUTH_MODE=all-except-health`.
- **Rollback**: one constant — the fallback in `parseConfiguredAuthMode` — and the policy is gone
  from the middleware signature (the previous two-argument calls are the pre-slice shape). Health
  and HMR route behavior does not depend on the resolver for correctness.
- The HMR gate's own loopback test now reads the same classification; it keeps its separate
  HTTPS/network rule (hot code loading is a different question from authentication).

## Residual work

- **Default flip to `auto`** — see the decision and reopen condition in I4.2.
- `off`-mode password changes: `sessionVia: "token"` is treated by the web app like any other
  non-desktop, non-setup session (old password required). If `off` becomes a shipped mode, the
  account menu must treat the grant like "setup" (random password never shown). Reopen condition:
  the default flip above.
- Per-request peer-address trust (accepting credentials-free requests only from an actual loopback
  peer) is deliberately not implemented; the bind is the trust boundary, as the card specifies.
