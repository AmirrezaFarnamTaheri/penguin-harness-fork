# 四处让键盘用户无法进入的修复

- **Date:** 2026-09-27
- **Type:** fix
- **Scope:** `web`

[English](2026-09-27-keyboard-reachability.md)

一次覆盖整个应用界面的审计找出了四处键盘无法抵达的地方。其中最严重的一处并不是缺少某个操作入口——而是一个控件对键盘而言根本不存在，而且那里没有任何替代路径。

## 细节

- **焦点环对白色的对比度只有 1.70:1**——不到 WCAG 2.2 SC 1.4.11 对非文本对比度所要求的 3:1 的三分之一，而且明暗两种主题下都是如此，作用于应用中每一个可聚焦元素。它是一个硬编码的 `rgb(107 114 128 / 0.4)`，即 40% 透明度的 gray-500，上面的注释却称其为"柔和的品牌色"。它并不是品牌色——这正是一个差了将近一倍的数值能够通过评审的原因。现在它改为 `var(--accent-bg)`，也就是样式表自己的注释中本就记录为该焦点环所用的 token：中性浅色主题下 17.7:1，深色基底上 19.1:1，蓝色强调预设下 5.2:1，并且会跟随用户选择的强调色——硬编码的数值做不到这一点。
- **日历的周视图有 168 个键盘无法抵达的创建入口。** 每个日期列的二十四个小时单元格是 `<div onClick>`：一周就是七列，也就是一百六十八处可以创建事件、而键盘根本够不到的地方，屏幕阅读器也从未被告知它们的存在。它们现在是真正的按钮，并采用**漫游 tabindex**——每个日期列只有一个 Tab 停靠点，方向键从那里在小时之间移动。把一百六十八个都变成普通的 Tab 停靠点，只是用一个更糟的问题替换了原来的问题。月份单元格有同样的缺陷，也采用同样的处理：由于该单元格容纳着当天的日程卡片，它本身不能作为按钮，因此控件是一个覆盖单元格顶部条带的真实按钮。
- **工单卡片曾是按钮套按钮。** 卡片带有 `role="button"`、`tabIndex={0}` 和一个 Enter/Space 处理器，而其中又包含一个用于指派人的真实 `<button>`。这是无效的 HTML，也是无效的可访问性树（SC 4.1.2）：辅助技术看到的是一个控件，而标记声明了两个，内层那个无法抵达。现在这个角色落在一个覆盖整张卡片的真实按钮上，它位于卡片自身内容之下，因此点击落点与此前完全一致。
- **现在有了跳转链接。** 侧边栏在页面首个控件之前有大约四十个可聚焦停靠点，因此使用键盘的用户每次打开应用都会落在导航区。该链接在获得焦点前位于屏幕之外，不需要任何状态或额外 CSS，并使用与其他控件相同的焦点环。它的目标带有 `tabIndex={-1}`——没有它，片段链接只会滚动到一个不可聚焦的元素、把焦点丢回 `<body>`，下一次 Tab 又从顶部开始，恰恰是这个链接要避免的情形。
